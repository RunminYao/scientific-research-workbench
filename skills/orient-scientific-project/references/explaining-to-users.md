# Explain a Scientific Project to a User

Assume the user may understand the research field without having followed the project's recent internal derivations, representations, numerical gates, or naming conventions. Do not infer complete project knowledge from repository ownership or earlier participation.

## Build an understanding bridge

- Answer the user's question first in plain language, then supply the minimum background needed to make that answer meaningful.
- Prefer a causal spine—question, obstacle, decisive result, present implication—over a chronological activity log.
- Define project-specific concepts at first use. Explain standard domain material only when it is a real dependency of the current conclusion.
- Translate formal distinctions that change interpretation, such as an intermediate variable versus a physical observable, a finite diagnostic versus a general result, or numerical agreement versus approximation validity.
- State why a result is nontrivial in terms of what plausible conclusion it overturns, rescues, narrows, or leaves unresolved.

Use layers when they help: a short answer, the mainline story, a background bridge, and evidence or limitations. These are choices, not mandatory headings. Match the user's language and requested depth; offer deeper equations or evidence routes without forcing them into the first explanation.

For a broad status question, center the active branch and the few developments that most recently changed its decision. Compress mature, frozen, or secondary branches to the contrast needed to understand that choice. In a first-pass orientation, leave equations, detailed numerical tuples, verifier tolerances, and older route inventories for follow-up unless one is essential to the user's question or changes the conclusion.

## Keep the main thread visible

- Mention failed paths only when they explain the current route, prevent a repeated mistake, or delimit the conclusion.
- Group related failures by the assumption or method they rule out. Do not make the user reconstruct the mainline from filenames, commit history, or a long stop ledger.
- Separate what the project originally set out to answer from a technically active branch when they differ.
- Make clear what is now known, what Codex currently judges, and what still requires a scientific decision.
- When recent work is relevant, distinguish committed results, working-tree developments, and freshly rerun checks instead of treating them as interchangeable.

Do not maintain a speculative profile of the user's knowledge or turn orientation into a quiz. Calibrate from the current question and correct course when the user asks for more or less background.
